# V8 项目结构问题清单

生成时间: 2026-06-08

## 总判断

当前 V8 项目最大的问题不是单个模块能不能跑, 而是版本边界和实验叙事已经开始混在一起。V8 本体其实是一个很干净的 critic 学法修正, 但项目里同时残留了 OACR、H-MCSS、PGW、buffer、Pareto memory 等多条探针线。如果不先收束, 后续实验很容易出现归因不清: 到底提升来自 clean critic, 来自 warm-start, 来自 buffer, 还是来自额外环境信息。

建议当前主线先收束为:

- 主模型: V8 = clean vector critic
- 待验证模块: PGW
- 暂时搁置: OACR
- 从主线叙事中删除: H-MCSS full3

## P0: 必须先处理的问题

### 1. 统一模型版本开关

问题:

`mofd_main.py` 默认配置中仍保留 `use_v5=True`, 但实际选择 V8 依赖 `use_v8=True`。这会导致配置文件里同时出现 `use_v5:true` 和 `use_v8:true`, 实验语义不干净。

风险:

以后复现实验时很容易不知道某次运行到底是 V5、V8, 还是 V5 配置下强行启用了 V8 类。

建议:

- 用一个字段替代多个布尔开关: `model_version = "v5" | "v8" | "v8_pgw"`。
- 删除或废弃 `use_v5/use_v8` 的混用写法。
- 保存 config 时明确写入最终解析出的 agent 类名。

验收:

- 每个 run 的 `config.json` 中只有一个模型版本字段。
- 日志明确打印 `agent_class = MOFD_SAC_V8` 或对应类名。

### 2. 明确 V8 的贡献边界

问题:

`mofd_v8.py` 只覆写两个 hook:

- critic target 去掉 entropy;
- critic loss 去掉 omega 权重, 只保留 PopArt 尺度归一。

这说明 V8 是 critic 学法修正, 不是完整新架构。

风险:

如果论文里把 V8 写成大模型创新, 容易被认为包装过度。

建议:

- V8 只写成 clean vector critic baseline / main backbone。
- 核心表述改为: 让 `Q_delay` 和 `Q_energy` 学成更干净的逐目标长期价值, actor 再按当前 omega 标量化选择动作。
- 不要把 V8 写成新的 diffusion policy。

验收:

- 方法章节中 V8 的贡献只对应 critic target 和 critic loss 两个公式。
- 不把 feedback diffusion 写成自有创新。

### 3. OACR 不能作为当前主线

问题:

OACR 初始 A/B 显示 late fusion 好, 但多批评估结果翻盘:

- late 赢 2/5 批;
- 平均 diff 为 -3.5%;
- 说明单批 +20% 很可能是 eval batch 运气。

风险:

如果继续把 OACR 写成稳定提升模块, 实验证据撑不住。

建议:

- OACR 当前状态标记为 failed probe / inconclusive probe。
- 不进入主模型。
- 如果以后重启, 必须先多 seed 重训, 不是只重载单 seed ckpt 多批评估。

验收:

- 主线 README / 方案文件中不再把 OACR 写成有效贡献。
- OACR 结果只放入内部诊断, 不进入论文主表。

### 4. H-MCSS full3 从主线删除

问题:

V8 的 H-MCSS 消融显示 `src_full3` 最差, `src_prior` 反而最好。说明三源候选 + 每步 critic 选优并没有带来收益。

风险:

如果论文继续 claim H-MCSS 是核心贡献, 会被自己的消融直接否定。

建议:

- 从主线贡献中删除 H-MCSS full3。
- 保留它作为失败消融或不写。
- 不再围绕 "三源候选融合" 设计新实验。

验收:

- 论文故事线里不出现 H-MCSS full3 作为正贡献。
- 代码中相关 runner 可以保留, 但注释改成 legacy/failed ablation。

## P1: 影响 PGW 是否成立的问题

### 5. PGW 的信息公平问题

问题:

环境 state 当前包含:

- task size;
- compute workload;
- omega;
- per-server `f_E`;
- `proc_queue_len`;
- valid flag;
- channel gain。

但不包含:

- base `tran_rate`;
- same-slot accumulated load `proc_queue_bef`。

而 greedy warm-start 使用了 `tran_rate` 和 `proc_queue_bef`。

风险:

PGW 如果赢, 可能不是因为 warm-start 方法好, 而是因为它使用了普通策略 state 中没有的信息。

建议二选一:

方案 A: 增强 state

- 把 `tran_rate` 和 `proc_queue_bef` 加入所有模型 state;
- V8、PGW、baselines 都使用同等信息;
- 增加 state-augmented V8 baseline。

方案 B: 限制 PGW

- PGW prior 只能使用当前 state 里已有的信息;
- 不允许 env-side 额外读取 `tran_rate/proc_queue_bef`。

验收:

- PGW 与 baseline 的输入信息完全一致。
- 论文中明确说明所有变量均为在线可观测, 且所有方法公平可访问。

### 6. PGW 必须证明 denoiser 不是照抄 greedy

问题:

PGW 的真正卖点不是 greedy warm-start, 而是 denoiser 能修正 greedy 的拥塞短视。但当前还缺少直接证据。

风险:

如果 final action 大部分等于 greedy action, PGW 会退化成披着 diffusion 外壳的 greedy heuristic。

建议:

补充机制日志:

- greedy action;
- final action;
- copy rate;
- final action 相对 greedy action 的 scalar cost change;
- wait delay change;
- queue imbalance change。

补充对照:

- hard greedy;
- soft-greedy-only;
- PGW-no-learn / identity denoiser;
- wrong-omega prior;
- state-augmented diffusion。

验收:

- PGW 不仅 HV 更高, 还要显示在高拥塞状态下 final action 会系统性偏离 greedy action。
- 偏离后 wait delay 或 scalar cost 有统计改善。

### 7. Greedy probe 的 HV 不能和模型 HV 直接横比

问题:

`pgw_greedy_probe.txt` 使用自己的 shared ref, OACR/H-MCSS 又使用各自 ref。不同 ref 下 HV 数值不能直接比较。

风险:

容易得出错误结论, 比如 "greedy HV 1292 大于 V8 HV 100/400"。

建议:

- 所有 PGW 对照统一 eval seed、n_epi、omega grid、HV ref。
- 用同一份评估脚本输出 A/B/C。

验收:

- 表中每个方法共用同一个 reference point。
- 输出文件明确保存 `shared_ref`。

## P2: 工程与复现问题

### 8. Monkey-patch runner 太多

问题:

OACR、H-MCSS、频率 sweep 等多个实验通过 monkey-patch 注入模型或环境, 长期维护风险高。

风险:

实验脚本之间互相污染, 或者保存的 config 无法完整表达真实运行路径。

建议:

- 建立统一 agent registry:
  - `"v5"` -> `MOFD_SAC_V5`
  - `"v8"` -> `MOFD_SAC_V8`
  - `"v8_oacr"` -> `MOFD_SAC_V8_OACR`
  - `"v8_pgw"` -> future PGW agent
- runner 只传 `model_version`, 不再 monkey-patch 全局变量。

验收:

- 任意 run 可以仅靠 `config.json` 恢复 agent 类。
- 不需要查看 runner 源码才能知道实际模型。

### 9. 结果目录命名和主线状态不一致

问题:

当前 results 中同时有 v8、oacr、hmcss、pgw_greedy_probe 等结果, 但哪些是主线、哪些是失败探针没有文件级标记。

风险:

后续整理实验表时容易误用失败或不可比结果。

建议:

- 新增 `results/README_results_status.md`。
- 标记每组结果:
  - valid main result;
  - diagnostic only;
  - failed ablation;
  - incomparable HV ref;
  - single-seed probe。

验收:

- 每个重要结果目录都有 status。
- 论文图表只从 valid main result 中取数。

### 10. 训练 seed 与评估 seed 证据不足

问题:

OACR 已证明单 eval batch 会误导。当前很多结论仍然是单 seed。

风险:

贡献点可能是训练随机性或评估环境随机性。

建议:

- 单 seed 只用于 go/no-go。
- 正式结论至少:
  - 3 个训练 seed;
  - 多批 eval seed;
  - mean/std 或 bootstrap CI。

验收:

- 主表不使用单 seed 作为最终结论。
- 单 seed 结果只写成 pilot/probe。

## 推荐执行顺序

1. 清理模型版本开关: 改成 `model_version`。
2. 把 V8 主线定义为 clean vector critic。
3. 将 OACR 标记为 failed/inconclusive probe。
4. 将 H-MCSS full3 从主线叙事删除。
5. 统一 HV 评估协议。
6. 决定 PGW 的信息公平方案: 增强 state 或限制 PGW。
7. 再做 PGW 单 seed go/no-go。
8. PGW 若过线, 再做多 seed 正式实验。

## 当前最该避免的错误

不要继续把所有模块叠在一起跑。现在最危险的不是模块不够多, 而是每个模块都可能解释同一个提升。先把主线收窄, 再加一个新模块, 才能知道到底是谁在起作用。
